# 我们放弃了截图流水线

*把文档构建从四分钟压到四百毫秒，中间只改了一个渲染器。*

---

过去每次发布文档，走的都是同一条路：Markdown 转 HTML，起一个无头浏览器，等它把
布局稳定下来，然后截图。这条路能跑通，但它有三个代价。

## 代价在哪

**慢。** 一个 800 × 4000 的页面，浏览器要跑完布局、加载字体、合成图层，再等
screenshot 触发。整站 40 个页面，一次构建四分钟，其中九成时间在等浏览器。

**重。** 我们的构建镜像里为了这一件事塞进了整个 Chromium，连同它自己的
依赖树——300 MB 镜像体积、四十多个传递依赖，只为了输出几张图。

**不可逆。** 位图一旦生成，后面就全不可逆了：文字变成了像素，不能搜索、不能复制、
不能重新排版。换个主题，整站重新渲染一遍。

> 位图是一句断言：文档到此为止了。它要求读者相信没有内容被裁掉、没有段落被重排。

## 现在的管线

三个阶段，每一层都是纯函数，各自都有独立的测试：

```text
Markdown 文本
  → 解析    (src/parse)   → Document
  → 排版    (src/layout)  → Scene
  → 输出    (src/engine)  → SVG | PNG | WebP
```

关键在中间那层。`Scene` 是一串扁平的几何图元——文本串、矩形、线段——坐标写在
基础单位里。往下的每一种格式都只是这个列表的一个序列化器，所以加 WebP 只花了
一个下午，而不是一个季度。

### 度量不依赖字体文件

排版引擎最自然的做法是读系统字体度量，但这会让输出随机器变化。这里改成内置一张
确定性字宽表，同一份文档在任何机器上断行结果都一样。

| 指标 | 截图流水线 | MarkPop |
|---|---|---|
| 冷启动 | 约 90 秒 | 约 0.4 秒 |
| 依赖 | 浏览器 + 系统库 | 无 |
| 文字 | 压平成像素 | 仍然是文字 |
| 确定性 | 取决于装了哪些字体 | 逐字节一致 |
| 远程图片 | 会去拉 | 永不拉取 |

## 结果

- 整站文档构建从四分钟降到两秒以内。
- 产出的 SVG 只有 38 KB，在浏览器里可以直接搜索。
- CI 镜像瘦了 300 MB，四十多个传递依赖消失。
- 没有人来问我们要回 PNG。
