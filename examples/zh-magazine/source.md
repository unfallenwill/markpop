# 文档的代价

*关于渲染、保真度，以及那些还能继续编辑的文件。*

截图是一句断言：文档到此为止。它把标题、列表、引用这些结构压成一个墨色的
矩形，然后要求读者相信这里没有内容被裁掉、没有段落被重排、也没有任何东西在
传递过程中丢失。

## 压平

压平本身并不是坏事。做缩略图、或者在信息流里放个预览，压平完全正确。问题在于
当压平的产物变成了唯一的产物。

文字一旦成了像素，三件事就会跟着发生：它不能再被搜索；它不能再被重排，所以窄屏
上要么无限滚动，要么被裁掉；它也不能再被改样式，换个品牌就得把每一页重新渲染
一遍。

## 另一条路

另一条路不是"更快的截图"，而是"一份从来就不是图片的文档"。

```rust
let svg = markpop::render("# 你好\n\n世界");
```

这次调用返回的是一段标记。里面的文字就是文字：可以选中、可以搜索、可以缩放到
任意尺寸，也可以交给另一个渲染器。几何信息保存在一份扁平的图元列表里，所以
序列化是唯一对输出长相有意见的部分。

> 文档是事实来源，图片只是它的一种渲染结果。

## 双栏

双栏改变的是阅读方式。窄的栏宽会逼出更短的句子和更快的段落。一整页密集的正文
会变成一页可以快速扫读的内容。

平衡分栏共享同一条流：引擎先找出能装下指定栏数的最短高度，再把内容尽量均匀地
分到各栏。内容不会丢失也不会重排，只是读者到达第一栏底部的时间比第二栏稍早
一点。

## 失去了什么

诚实起见，得把损失列出来。没有语法高亮，因为高亮器是另一个程序，它对词法切分
有自己的主张。没有远程图片抓取，因为会联网的渲染器是会卡住的渲染器。也没有
HTML 执行，理由和"文档不该在显示它的机器上跑代码"完全一样。

其余的一切——强调、代码、表格、引用、任务列表，还有你自己写的脚注——都在那里，
而且归你重新配色。

## 收尾

评价任何一个渲染工具，该问的不是它有多快，而是它留下了什么。好的工具会把文档
原样留下。
